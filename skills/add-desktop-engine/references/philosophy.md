# Design philosophy

These principles come from decisions actually made while building Frontdesk. Each one says why it exists; when a situation is not covered, reason from the "why".

## 1. Frontdesk is a go-between, not another AI

1. **Execution and history belong to the desktop app.** Frontdesk only carries messages: it puts what the person says into the desktop app's own execution path and shows the history the desktop app wrote. It does not rewrite the agent loop, call model APIs itself, or keep a chat record of its own.
   Why: the person wants "my Claude / Codex / …", not a look-alike. With one shared history, either side can pick up where the other left off.

2. **Read local data only; write only through the desktop app's own process.** Session files and databases are opened read-only. For sending, prefer officially published means (SDK, app-server, a local service's interface), but only when this turn is run by the desktop app's own process, the desktop app shows the message right away as the person's own, and no one else's token is used (the three questions in [Choosing channels](channels.md)).
   Why: private sockets, forged input and reading another process's tokens either give the message the wrong identity (treated as "sent from another session") or need credentials you have no right to, and they break with any release. Frontdesk hit exactly this early on; see `docs/development-history.md`.
   When the official channel can only continue a session in a separate process (Claude's CLI, for example), that process and the desktop app each keep their own context and do not share the prompt cache. Then, with the person's authorization, use the system's Accessibility features to press Send in the desktop app on the person's behalf, in the background (Claude's "desktop send", `src/server/claude-desktop.ts`): the message's identity is the person's own and no token is read. Conditions: never activate the app or take focus; check the result of every step, and count a send as successful only once the session record shows the message; when it cannot be done, do not send and say why (never fall back to the separate-process channel).
   Likewise: when the official channel cannot join a turn the desktop app is running, use the channel the desktop's own windows use to cooperate, and let the window that holds the session take the message. For example Codex's `thread-follower-steer-turn` (`src/server/codex-desktop.ts`): Frontdesk briefly connects to `~/.codex/ipc/ipc.sock` as a "follower" and asks the desktop window to put the message in. The effect is the same as typing in the desktop app; no token is read and no file is touched. Same conditions: the native record decides; when no desktop window holds the session or the turn has already ended, fall back to the queue; never resend after a timeout.
   Another example, sending in an existing Codex chat: Frontdesk's own app-server only uses `thread/queue/add` to put the message in that session's official queue (without loading the session or taking its writer lock), then `open -g codex://threads/wake/<id>` wakes the desktop app, whose own app-server takes over and runs it. Do not `thread/resume` / `turn/start` on Frontdesk's app-server: the writer lock would land on Frontdesk's process and the desktop app would show "This is open in another app". New chats likewise are started by the desktop app itself (Accessibility picks the project on its New chat page, fills in the message and presses Send).
   **Write the Accessibility helper as page objects; do not write a separate one per engine.** The actions are shared (`src/server/native/ax-driver.swift`: find controls, press, fill, open and close menus, refresh off screen); each engine writes only its own steps (`src/server/native/<engine>-desktop.swift`); what the controls are called, the sidebar title suffix and deep-link templates are data (`src/server/native/profiles/<engine>.json`). Success is judged by the native record, not the interface. Off screen, Chromium only updates its accessibility tree near the element that received an action, and an open menu hides the page behind it from the tree, so the refresh while waiting must land on the open menu's own button (the driver's `anchor`), not on the composer.

2a. **Your own sign-in credentials may be used; nobody else's.** "Other programs" means other engines, other apps, and private tokens between your desktop app's own processes (for example a peer socket's token). The credentials your own official CLI / SDK saved for signing in (for example the OAuth token Claude Code keeps in the Keychain item "Claude Code-credentials") exist for your official features: Frontdesk may use them on the server to call your own official interfaces (quota, speech recognition), under the conditions of principle 15.
   Why: in a rehearsal, Claude treated reading its own token as a violation and skipped dictation; since dictation is provided by Claude for every engine by default, all three engines lost it.

3. **No read-only mode, and no blocking sends while the desktop app is running.** The person explicitly chose to make sure they never write to the same session from two places at once. So `blocked()` only expresses "this really cannot be sent" (not signed in, not installed, no channel); never return a reason because "this session is running in the desktop app" and never make the composer read-only. When a session is running in the desktop app, mark it honestly with `isDesktopActive` and keep sending available. After Frontdesk sends, the desktop app may need to reopen the session to catch up (mention this in your report).
   Why: the person said "I will make sure I never write at the same time." Adding a lock for them overrides their choice; explain the consequences and let them decide.

4. **The person's settings follow the message.** A turn sent from Frontdesk uses that session's model, reasoning effort and permission mode from the desktop app; with no record, it uses the settings of the most recent desktop session. What the person changed in Frontdesk is changed through the desktop app's own channel, inside the desktop app (Claude uses Accessibility to operate the model and permission menus under the composer; Codex asks the window that holds the session to change it, which runs what its model menu runs, and uses the menu only when that cannot be done), and then sent, so the desktop app shows and keeps the setting used. When the desktop app cannot make the change, do not send and say why; never quietly send with the old settings.
   Why: a turn sent from Frontdesk should be the same as one sent in the desktop app, including whether it asks for permission.

## 2. Honesty

5. **Status needs evidence.** "Completed", "failed" and "stopped" are shown only when the native record has matching evidence. Being idle, a file's modification time, one failed command, a temporary retry: none of these means the task ended. When unsure, show that it is being confirmed.
6. **Say what cannot be done, why, and what to do next.** Cannot send, not signed in, no quota available, no stop interface: say it in one plain sentence in the interface and tell the person what to do (for example "run `claude auth login` once in a terminal"). Never leave the interface stuck on "sent".
7. **Never make up data.** Model lists come from an interface the engine exposes or aliases in its documentation; quotas come from the engine's own quota interface; when they cannot be had, show that.

## 3. Familiar: shared structure, individual details

8. **Coding agents' chat pages share one set of components.** Chats grouped by project and loose chats, collapsed commands and tool calls, step lists, question / summary cards, the model / reasoning effort / permission menus under the composer, files you can open: almost every coding agent's desktop app has them. Frontdesk made them a ready-made chat kit (`src/client/kit/`), defaulting to a "Claude style" measured from the Claude desktop app. A new engine connects its data, and it works.
   Why: screenshotting, measuring and matching every engine one to one is expensive and error-prone (most rehearsal problems came from there). Doing the shared structure once, well, benefits every engine, and the person manages several agents in one familiar interface.

8a. **No native element of a conversation may be missing.** In a conversation a desktop AI lists steps, runs commands, takes screenshots to check results, gives summary cards and asks the person questions. These are its abilities made visible, and they must all appear in Frontdesk and work (question card buttons can be pressed, files can be opened).
   Why: this is how the person tells "what is it doing and how far has it got"; without them, however good the page looks, it is just a chat log viewer.

8b. **Fill in what is distinctive with variables and renderers, not a copy.** Brand colour and typeface differences go into the kit's `--kit-*` variables; things the kit lacks (a card only one engine has) get a registered renderer. Only when the person explicitly asks for "exactly like my desktop app" do you do a one-to-one match (`ui-fidelity.md`).
   Why: if you copy the styles to change them, the kit's later fixes never reach you; variables and renderers keep the shared parts consistent.

9. **What belongs to Frontdesk is the same for every engine.** The agent rail on the far left (engine entries, character avatars, unread badges, quota bars and their hover cards, the speech bubble), the layout of the sidebar and the chat header, the dictation button's behaviour, approval cards, the settings panel, theme switching. Engines take part through data, not by changing their style or behaviour.
   Why: this is the cross-engine "console"; it must be consistent to compare at a glance and switch in one click.

10. **Custom controls, not system controls.** Dropdowns, menus and dialogs use Frontdesk's own components (`src/client/js/menu.ts`), with a neutral focus outline. A skin may change how they look to resemble the desktop app, but never swaps back to the system's native dropdown.

## 4. Characters and speech

11. **Each AI uses its own character.** Prefer the character / mascot that ships with the desktop app (Codex's little cloud robot, Claude Code's pixel Clawd), read at run time from the app installed on this machine, never copied into the project. Without an official character, use an original one clearly marked as a "stand-in", coloured from the brand.
12. **The speech bubble holds only what the AI says.** Everything the AI says while working (including progress notes midway) goes into the bubble, trimmed to one sentence; tool calls, commands and thinking never do. The character moves while the AI works, and the bubble types out what it says. The bubble is lettered the way a comic letters one: small (three lines at most), sitting on the frame between the rail and the window, rising beside the avatar, and translucent; it leaves by itself once read and fades from under the pointer, so it does not block the list beneath. While the AI works with nothing new to say it shrinks to three dots by the avatar; a line you missed is still in the hover card.
13. **Quota must be readable at a glance.** One segmented bar under the avatar, in the engine's brand colour: a segment for every window the engine reports (5 hours, weekly, per model… however many limits the account has), and the segment that is nearly used up turns red. Only hovering the avatar shows a card with each window's name, value and reset time.

## 5. Small and steady

14. **Extension points first; leave the core alone.** New engines join through plugins and skins; routing, events and front-end dispatch never hard-code any vendor.
15. **Privacy.** Tokens are used only on the server, never reach the page, logs, tests or any file. Features needing sign-in (dictation, quota) are relayed through the server, read fresh each time, never cached to disk.
16. **Degrade gracefully.** Any parsing that depends on a private format must tolerate errors: skip records you cannot read instead of failing the whole session.
17. **No shared capability rests on one engine.** The person may not have a given AI installed at all, so no engine may be a precondition for another. Dictation works this way: any engine's speech-to-text can serve any chat, and the microphone takes the first one that can start now, in this order: the person's pick in settings → the default (`BRIDGE_DICTATION_ENGINE`, default `claude`) → the current engine's own → the other engines' → the browser's own (`src/shared/dictation.ts`). If your desktop app has speech-to-text, wire up `dictate`, and say through `dictationReady` whether it can start now and why not (signed out, not running), so that when it cannot, the microphone moves on to the next one and tells the person why.
18. **Screenshots contain the person's real chats.** Desktop screenshots and automatic captures include the person's conversations and file names. Raw screenshots go only in `docs/skins/<id>/source/` (ignored by `.gitignore`) or your temporary directory; the repository keeps only cropped comparison images with nothing private. Continuous automatic capture (every few seconds, say) needs the person's consent first and must be stopped as soon as you are done.
   Why: the project is going open source, and in a rehearsal screenshots put about 10 MB of real chats into the docs directory.
