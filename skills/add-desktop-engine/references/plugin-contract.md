# Plugin contract

**`src/shared/contract.ts` is the source of truth.** This file explains those types: the exact shape of every field and method is in the types, which the server and the page share, and a plugin with a wrong field or a missing required method fails `npm run build` / `npm run typecheck`. Where the two disagree, the types win, and you fix this file. Mapping: the plugin's argument is `PluginSetup` / `PluginContext`, `registerEngine()` takes an `Engine` (= `EngineDeclaration` fields + `EngineMethods` methods), capability flags are `Capabilities`, `look` is `Look`, `spaces` is `Space[]`, sessions / turns / steps are `UnifiedSession` / `UnifiedTurn` / `UnifiedStep`, engine events are `EngineEventMap`, and the SSE events the page receives are `BridgeEventMap`.

The existing `src/server/plugins/codex.plugin.ts`, `claude.plugin.ts` and `antigravity.plugin.ts` are the living examples. This file lists the shapes you must follow. How each capability is used on the page and how its requests travel is in [Capability paths](capabilities.md); which route a message takes into your desktop app is in [Choosing channels](channels.md).

## 1. The plugin file

`src/server/plugins/<id>.plugin.ts` (TypeScript) exports two things: `export const about: PluginAbout` (who you are, and whether your desktop app is on this machine) and `export const setup: PluginSetup` (taking `{ config, registerEngine, registerAsset }`; it may return a function that releases resources). The server is ESM, so relative imports end in `.js` (the compiled file's name).

```ts
// src/server/plugins/myagent.plugin.ts
import type { PluginAbout, PluginSetup } from '../../shared/contract.js';
import { appPlaces, firstExisting } from '../services/app-assets.js';
import { CHAT_CAPABILITIES } from '../services/desktop-chat.js';
import { MyBridge } from '../myagent-bridge.js';

// Frontdesk knows you while you are switched off too: your name, icon, colour, and whether your desktop app is on this machine.
const IDENTITY = { id: 'myagent', label: 'MyAgent', description: 'MyAgent desktop', priority: 40,
  accent: '#7A5AF8',                            // brand colour: the mark on the agent rail, the quota bar, the speech bubble, the unread dot and current-row mark in the window
} as const;
export const about: PluginAbout = { ...IDENTITY,
  appIcon: '/Applications/MyAgent.app/Contents/Resources/icon.icns',   // your installed app's own icon, the fallback when there is no character; Frontdesk reads and serves it at run time, never commit a copy
  detect: () => firstExisting(appPlaces('/Applications/MyAgent.app/')) };

export const setup: PluginSetup = ({ config, registerEngine, registerAsset }) => {
  const bridge = new MyBridge(config);
  registerEngine({
    ...IDENTITY,
    character: { kind: 'image', url: '/api/characters/myagent' },   // see section 4
    permissionModes: [{ id: 'ask', label: 'Ask', description: '执行前先问你' }],   // optional, see section 6
    skin: { stylesheet: '/skins/myagent/skin.css' },   // optional: change --kit-* variables, add what only you have
    look: { worked: 'fold' },                     // optional: how your desktop app writes a turn (section 7, "How a conversation looks")
    spaces: [{ id: 'chat', label: 'Chat', capabilities: CHAT_CAPABILITIES }, { id: 'code', label: 'Code', default: true }],   // optional: the mode switch at the top of your desktop sidebar (section 7)
    capabilities: { attachments: true, cwd: true, models: true, reasoning: true, interrupt: true, steer: true, approvals: false, dictation: false, send: true, openFile: true },
    status: () => bridge.status(), models: () => bridge.models(),
    list: () => bridge.list(), read: id => bridge.read(id),
    create: input => bridge.create(input), send: (id, input) => bridge.send(id, input),     // required
    interrupt: (id, emitter) => bridge.interrupt(id, emitter),   // optional by capability: stop; steer, sendNow, decide, observe (steer, send now, answer cards, follow a turn Frontdesk did not start) the same way
    // usage, dictate, media, blocked, projects, openFile, fileRoots,   // optional by capability
    // newOptions, pickNewOption, pickNewOptions, newSettings,          // optional: the desktop's new-chat page (see "Sidebar and new chats")
  });
  return () => bridge.dispose();
};
```

`id` may contain only lowercase letters, digits and hyphens. `priority` sets the order on the agent rail, top to bottom (Codex 10, Claude 20, Antigravity 30).

**Switching on and off (hot swap).** When Frontdesk starts it reads `about` only and does not call `setup`: an agent that is off starts no bridge, holds nothing and reports no errors; it is just a row under "Add an agent". `setup` runs when the person turns the switch on (the rail's "+", settings, or the first page shown while no agent is on). When they turn it off, Frontdesk first takes away the engine and assets you registered and lets go of what it kept for you (turns it follows, queued messages, observers, cached usage, open event streams), then calls the function `setup` returned. So:

- Nothing in `about` may have side effects. `detect(config)` only looks for the desktop app (does its bundle, or its own data folder, exist; `src/server/services/app-assets.ts` has `appPlaces` / `firstExisting`); it starts nothing and reads no private data. Until the person chooses, an agent is on when its app is found and off when it is not; once they choose, their choice wins (kept in `.frontdesk.json` at the project root; `BRIDGE_SETTINGS_FILE` moves it). A plugin without `detect` counts as found.
- `setup` is called more than once (off, then on again). Build your bridge afresh each time, and have the returned function release everything that call made (child processes, timers, file watchers, what `registerTool` returned). Keep no global state. If `setup` throws, the agent stays off and its row shows the reason.
- Switching off never touches the desktop app: a turn that is running keeps running there; Frontdesk only stops following it.
- `about.id` is the id of the engine you register, and `about` and `registerEngine` share one copy of the name, icon and colour (`IDENTITY` above); do not write them twice.

## 2. Required methods

| Method | Returns | Notes |
| --- | --- | --- |
| `status()` | `{ connected, error? }` | `error` is a sentence for the person, such as "not signed in, run …". |
| `models()` | `[{ id, name, description?, hint?, reasoningEfforts?, defaultReasoningEffort? }]` | Only what can be discovered or is documented. `description` shows in the model menu under the name (hidden in the kit). With `reasoningEfforts`, an effort menu appears under the composer. |
| `list()` | `UnifiedSession[]` | See section 3. Must be fast: cache large files by size / modification time. |
| `read(id)` | `{ session, turns }` | See section 3. |
| `create(input)` | `{ id, cwd?, started? }` | `input`: `{ cwd?, model?, reasoningEffort?, permissionMode?, title? }`; engines declaring `createRequiresPrompt` also receive `prompt` and `attachments`. If creating also runs the first message, return `started: true` and implement `observe`. See "New chats" below. |
| `send(id, input)` | `EventEmitter` | Returned synchronously; events start only after `queueMicrotask`. `input`: `{ prompt, cwd, model, reasoningEffort, permissionMode, attachments: [{ path, originalname, mimetype }] }`. Follow [Choosing channels](channels.md) so that the desktop app's own process runs the turn; the message counts as sent once the native record shows it. When `model` etc. differ from the desktop's current settings, change them in the desktop app first, and if that fails, do not send (section 6, `permissionModes`); what is not given keeps this session's desktop settings. `permissionMode` accepts only ids you declared in `permissionModes`. |

## 3. Data shapes (`src/shared/contract.ts`; helper constructors in `src/server/types.ts`)

Treat native records (session files, interface responses, chats read through accessibility) as `unknown` first and narrow them into the shapes below with `get` / `str` and friends from `src/shared/guards.ts` and your tolerant parsing, skipping records you cannot read; never use `as` to pretend you know a native format.

- `UnifiedSession`: `{ id, engine, title, updatedAt, cwd, status: 'idle'|'busy', isDesktopActive, sendBlocked, metadata }`.
  - `sendBlocked`: a non-empty string means it cannot be written to now; the string is the reason shown.
  - `metadata.recentMessages`: `[{ id, preview, phase, at }]`, the last few things the AI said (the AI's own words only, no tools or thinking). `id` must match the message ids in `read()`. **This is the source for the speech bubble on the agent rail**: without it, what sessions driven from the desktop say never reaches the bubble.
  - `metadata.turnStartedAt` (optional): when the latest turn started (milliseconds or ISO). When polling finds a session running, the shared layer uses it as the start of that turn, and the avatar's bubble shows only what was said after it; without it, the moment of discovery is used. `at` must be the message's own time, not the time it was read.
  - `status: 'busy'` must be backed by the native record. Claude's example: `latestUserFrameAt` later than `lastTurnEdgeAt` in the desktop index does not necessarily mean running (changing settings in the desktop menu leaves that frame too); if the session record shows the turn wrapped up and nothing was written for 90 seconds after the frame, it counts as idle (`sessionRunning`).
  - `metadata.latestTurn` (optional): `{ id, status, completedAt, statusEvidence }`, the latest turn's status with evidence.
  - Session data the kit uses (all optional; the more you give, the more the sidebar and composer look like your desktop app):
    - `metadata.group`: the project this session belongs to in your desktop sidebar. Three values with different meanings; **do not guess from `cwd`**:
      - `{ id, name, cwd? }`: in this project (or a group the person made). `id` is the desktop app's own project id; `cwd` is the project's folder, used for new chats.
      - `null`: explicitly in no project, filed under "Chats" in the sidebar. Temporary folders the desktop app makes for such chats (Codex's `~/Documents/Codex/<date>/<name>`, for example) are not projects.
      - Absent: the shared sidebar falls back to the `cwd` folder name as the project, and sessions without `cwd` go under "Chats". Use this only when your desktop app really groups by folder.
      - First look where the desktop app records membership (a project field in an official interface, the desktop app's own state file), then fall back to "a project's root folder contains `cwd`". See `src/server/services/codex-projects.ts`.
    - `metadata.parentId`: the parent session's id; sub-sessions hang under it.
    - `metadata.attention`: non-empty means the person needs to act; the sidebar row ends with an orange dot.
    - `metadata.desktop`: `{ model, effort, permissionMode }`, this session's settings in the desktop app. The composer's menus start on them; otherwise `metadata.model`.
    - `metadata.desktopQueue` (on the session `read()` returns): `[{ prompt, at }]`, messages the desktop app is holding to put into the running turn (Claude replays them from the record's `queue-operation`s). The page shows "<your name> queued" above the composer, with a "Send now" button if you have `sendNow`. Return an empty array when no turn is running.
- `UnifiedTurn`: `{ id, userPrompt, userImages, timestamp, status, statusEvidence, completedAt, messages, timeline, steps, artifacts }`.
  - `userImages`: `[{ url, alt }]`, images the person pasted into this message, with `url` under the same rules as `step.images` below. Shown above the person's message; clicking opens the full image. Remove image placeholder text the desktop app adds to the person's text (for example `[Image: source: …]`).
  - `messages`: `[{ id, text, phase: 'commentary'|'final_answer' }]`. Mark them with `assignPhases(turn)`: anything followed by more tool activity is commentary, the last part is final_answer.
  - `timeline`: `[{ kind: 'message'|'activity', id }]`, in true order.
  - `steps`: `UnifiedStep { id, type, name, input, title, detail, output, status, paths }`. `name` and `input` are the native tool name and arguments, summarised by `src/server/services/tool-catalog.ts`; for a new tool's summary, add one `registerTool` rule.
  - `step.plan`: `[{ content, status: 'pending'|'in_progress'|'completed' }]`. Your step list (Claude's todo tool, Codex's plan updates, for example). Steps with `plan` stay out of tool groups and are drawn as a step card; only the latest one per turn is shown.
  - `step.images`: `[{ url, alt }]`, where `url` must be `/api/sessions/<engine>/<sessionId>/media/<key>`, served by your `media(sessionId, key)` returning `{ type: 'image/png'|'image/jpeg'|'image/gif'|'image/webp', data: Uint8Array }` (a `Buffer` is fine), that is, a `MediaFile`. For screenshots in tool results and generated images. Images from any other source are dropped.
  - Question / summary card: a step with `type: 'summary'` (map your native tool to `type: 'summary'` with `registerTool`), whose `detail` is the JSON string `{ recap, ask, actions: [{ label, app }] }`. The kit draws it at the bottom of the turn, only on the latest turn, and only when there is an `ask` or `actions`. A button with an empty `app` sends its `label` as the next message; a button with a non-empty `app` is the desktop app's own action (commit, open a PR…). The desktop decides what these buttons are called and which ones there are: the record's `label` is not necessarily the text the desktop draws, and the desktop draws only those it can run at that moment, so never hard-code a table of names. An engine that declares `capabilities.cardActions` implements two methods: `readCard(id, { ask, recap, replies })` (`WrapUpCard`) reads the names of the desktop's own buttons off its card and returns them in order as `{ actions }` (`CardRead`); `pressAction(id, { ask, recap, replies, index, label })` (`CardAction`) presses the one at `index`, so the desktop does it just as if the person had clicked there. The card is found by its `ask`, or its `recap` without one; the desktop's own buttons are the card's buttons other than its close button (the profile's `cardSkip`) and the `replies` (the reply buttons' words, which the record has), looked for only in the conversation (the `transcript` locator) so that a button on another web page in the same window is never taken. When such a card appears on the latest turn the page reads it from the desktop once (`POST /api/sessions/:engine/:id/card`); before that, or when it cannot be read, the record's names are shown disabled, and afterwards the desktop's names and count are drawn; a click goes to `POST /api/sessions/:engine/:id/actions`. When a button cannot be pressed, throw an error with the reason (the turn is still running, the button is no longer on the card), and never turn it into a message. For an engine without it, these buttons are shown disabled. See Claude (`card` and `action` in `claude-desktop.swift`).
  - Only a person's input starts a new turn. Injected system context, image captions, compaction summaries and sub-agent records do not.

## 4. Characters

- `{ kind: 'image', url }`: one image (SVG/PNG), placed in the round avatar.
- `{ kind: 'sprite', url, columns, rows, cell: [w, h], idle: [col, row], working: { row, frames } }`: a sprite sheet; idle shows the `idle` cell, working loops the first `frames` cells of row `working.row`.
- Images from a desktop app installed on this machine are read at run time with `registerAsset(name, () => ({ type, data }))`, with `url` set to `/api/characters/<name>`. An Electron app's resources are in `app.asar`; read them with `readAsarFile(asarPath, /pattern/)` from `src/server/services/app-assets.ts`. Never copy these images into the project.
- No official character: draw an original stand-in in brand colours at `src/client/public/assets/characters/<id>.svg` and say in an SVG comment that it is a stand-in.
- Browsers cache character images for a day. When you change how the image is drawn or the cell size, put a content-based version in the `url` (for example `/api/characters/<name>?v=<first characters of a content hash>`), or the browser pairs the old image with the new cell size and the avatar is cropped crooked.
- Make each sprite cell square with the character centred; the working frames share one centred box so the animation does not jitter. The avatar is round, so content off in a corner looks crooked.
- In the console's settings the person can rename an agent, reorder the rail, and upload their own idle / working pictures for its face (`src/server/core/agent-looks.ts`, kept in `.frontdesk.json` and `.frontdesk-avatars/` beside it). The console merges these into `/api/engines`; a plugin does nothing. Whatever they have not changed is your declared `label` and `character`, so your default face is the one they see first.

## 5. Events (the EventEmitter returned by `send` / `observe`)

| Event | Data | Purpose |
| --- | --- | --- |
| `item_completed` | `{ item: { type: 'agentMessage', id, text, phase } }` | A finished piece of what the AI said |
| `item_started` | `{ item: { type: 'agentMessage', id, text, phase } }` | A reply the desktop app is still writing: its whole text so far, sent again as it grows (a few times a second at most), with the same `id` as the `item_completed` that ends it. A record on disk usually has a reply only once it is whole; take the text so far from where the desktop app keeps it live (Codex: the owning window's state through `watch`; Antigravity: the language server's step while it is `GENERATING`), and stop once the record has the reply |
| `delta` | `{ type: 'agent_message', id, text, phase }` | Streamed text to append |
| `delta` | `{ type: 'tool_call', id, name, input, plan? }` / `{ type: 'tool_result', id, output, isError, images? }` | A tool starts / ends; `plan` is the latest step list, `images` as in section 3 |
| `delta` | `{ type: 'command_output', id, output }` | Command output to append |
| `delta` | `{ type: 'reasoning' }` | Only "thinking", with no content |
| `artifact` | `{ path, title?, kind? }` | An artifact: something your desktop app itself draws as a file card in this turn (same rule as `artifacts` in history). Frontdesk does not draw a card just because a tool read or edited a file; if your desktop app shows no card, do not send one |
| `approval` / `approval_resolved` | `{ id, title, detail, decisions }` / `{ id }` | Something waiting on the person, drawn as a card under this turn's reply: a permission prompt (`decisions: ['accept', 'decline']`) or the AI's own multiple-choice question (`decisions: [{ id, label }]`, using the desktop app's own option text). Whatever the person picks calls `decide(id, <option id>)`; when answered in the desktop app, send `approval_resolved`. Never make it a sidebar marker. Build question cards with the shared `questionCard(id, questions, appName)` (`src/server/core/presentation.ts`). Answers go through the desktop app's own channel: through an interface where there is one (Antigravity: `askOf` / `decide`); otherwise the helper picks on the desktop's card (Claude: the shared driver's `answerCard`, with `questionSubmit` / `questionSkip` in the profile); where the desktop's windows have a coordination channel, through that (Codex: follow the window holding the session to get its pending requests via `watch`, answer with `thread-follower-submit-user-input` / `*-approval-decision`). The answer counts once the native record shows it. |
| `warning` | `{ message, retrying }` | A recoverable problem |
| `completed` | `{ reply?, turn?: { status } }` | The turn ended (with evidence) |
| `error` | `Error` (`err.transport = true` means a connection problem, not a failed task) | |

Set `emitter.turnId` to the native turn id to help reconcile after a disconnect.

## 6. Optional capabilities

- `interrupt(id, emitter)`: stop. Returning `{ pending: true }` means you asked the desktop app to stop and will report the final state from the native record yourself (`completed { turn: { status: 'interrupted' } }`); otherwise RunService marks it stopped at once. `capabilities.interrupt` enables Stop for turns Frontdesk tracks. Plugins that declare `desktopInterrupt: true` can also stop desktop turns when there is no `emitter`.
- `steer(id, input, emitter)`: steer, putting a message into the turn that is running (the person presses Enter while running, or "Insert" in the queue). Called only with `capabilities.steer: true`. The native record or the desktop's confirmation decides; **when it cannot join, throw `Object.assign(new Error('<reason>'), { fallback: 'queue' })`**, and the message goes into Frontdesk's queue automatically with the reason shown; a confirmation that timed out throws an ordinary error (with `status`), and is never resent. Returning `{ shown: false }` means your live events already drew this message as a user message; otherwise RunService adds a steer bubble to this turn.
- The queue needs no implementation: when the person presses Tab while running (or the engine has no `steer`), the message is kept in `RunService`'s in-memory queue and sent in order once this turn ends and `read()` shows the desktop app is not running either (a session `status: 'busy'` or a last turn `status: 'running'` both count as running). So `read()` must reflect "running" honestly.
- `sendNow(id)`: only if your desktop app has its own "send now" (putting the message it is holding into the turn at once), like Claude's Send now; return `{ status: 'sent' }`, or throw an error with the reason.
- `blocked(id)`: returns the reason it cannot be written to, or an empty string if it can. The server calls it before sending and when reading a session. Only for "this really cannot be sent": not signed in, not installed, the desktop channel unavailable. **Never** return a reason because the session is running in the desktop app (philosophy 3); mark that with `isDesktopActive: true` instead: the shared interface shows "active in the desktop app" in the session info and sending stays available.
- `usage()`: `{ available, windows: [{ id, label, windowMinutes, remainingPercent, usedPercent, resetsAt (seconds) }], short?, reason? }`. Each window is a segment of the quota bar under the avatar and a row in the hover card, in the order you give them (eight segments at most on the bar); give one window per limit the account has. When unavailable, `available: false`, `short` is a two- or three-character status ("未登录"), `reason` the full explanation.
- `dictate({ language, onText, onError, onEnd })`: returns `{ send(pcm16kMono), finish(), cancel() }`. Any engine's speech-to-text can serve any chat and none is required: Frontdesk takes the first one that can start, in the order of `src/shared/dictation.ts` (by default `BRIDGE_DICTATION_ENGINE`, Claude, is tried first), moves on when one cannot start, and ends with the browser's own. When `dictate` cannot start, throw an error that says why: Frontdesk tries the next one and tells the person.
- `dictationReady()`: returns `{ ready, reason? }`, whether `dictate` can start now and why not (for example "Claude Code is signed out", "Antigravity isn't running"). A cheap check only: it reads no token contents and touches no audio. Frontdesk keeps the answer for a few seconds; the microphone's tooltip and the "Uses now" line in settings depend on it. Without it, Frontdesk just tries `dictate`.
  - How Claude does it: on the server, read your own OAuth token fresh from the Keychain item "Claude Code-credentials" (`security find-generic-password -s "Claude Code-credentials" -w`), connect to `wss://api.anthropic.com/api/ws/speech_to_text/voice_stream?encoding=linear16&sample_rate=16000&channels=1&endpointing_ms=300&utterance_end_ms=1000&language=<lang>&use_conversation_engine=true` with `Authorization: Bearer <token>`; receive `TranscriptInterim` (interim) / `TranscriptText` (final) / `TranscriptError`, send `KeepAlive` periodically and `CloseStream` at the end. When stopped, replace the interim results with the final one. This reads your **own** credentials (philosophy 2a) and is allowed; the token never reaches the page, logs, tests or files.
  - Other engines with their own speech-to-text should wire it up too: when the person has no Claude, or is signed out of it, the microphone uses theirs (Antigravity uses its language server's `StreamAudioTranscription`).
  - Tests use doubles for the Keychain and the WebSocket and never connect to the real service.
- `media(sessionId, key)`: returns one image from the session (see `images`, `userImages` in section 3). Read-only, from the native record.
- `permissionModes` (a plugin field, not a method): `[{ id, label, description }]`, the permission modes your channel accepts; `id` letters only. Once declared, a permission menu appears under the composer, starting on `metadata.desktop.permissionMode`; the selected value reaches `send` as `input.permissionMode`. When `input.model / reasoningEffort / permissionMode` differ from the desktop's current settings, the person changed them in Frontdesk: engines sending through the desktop must change the setting in the desktop app first (see `applySettings` in `src/server/native/claude-desktop.swift`), and if they cannot, not send and return the reason. Without it there is no such menu.
- File preview needs nothing from you: file paths in the text (links, or inline code like `src/server/a.ts:42`) become links automatically, and Frontdesk previews files in the session's `cwd` read-only (refusing key files and `.git`). Just make sure `read()` returns the right `session.cwd`.
- The small box that appears when hovering a file link, and the right preview's title bar, offer "Show in Finder" (shared; server `POST …/reveal { where: 'finder' }`; nothing for you to do) and "Open in <your name>". The latter needs `capabilities.openFile: true` and `openFile(id, { path, absolute, relative, label })`: open this chat in your desktop app, press the chat's own link to the file (opening it however your desktop app does), then bring the desktop app to the front. With the shared driver, call `DesktopAutomation#openFile({ title, localId, path, absolute, label })` (the driver's `open-file` command; nothing to write in your flow); `{ pressed: false }` means only the chat was opened and no link was found, and the page says so. A desktop app that is itself an editor with no Accessibility flow (Antigravity) just opens the file. The server has already checked the file is inside the session's `cwd`, or inside the folders your optional `fileRoots(id)` returns (an array of absolute paths: where your desktop app saves documents for this chat, such as Antigravity's `brain/<id>`). Links in replies may point at folders (`docs/`) or `file:///…`; the preview panel lists a folder's contents.
- The "Open this chat in the desktop app" button at the top right of the chat header: declare `capabilities.showInDesktop: true` and implement `show(id)`, which shows this chat in your desktop app and brings the app to the front. Every engine is expected to have it: with an Accessibility flow, use the shared `DesktopAutomation.showSession({ title, localId?, space? })` (the driver's `show-session`; the desktop stays in the chat's mode), which needs only a profile even where nothing else goes through the window (Antigravity's flow has no steps of its own); for a cloud chat mode's chats use `mode.show(id)`. Where the desktop's page has an address for each chat, the profile's `sessionAddress` (`"/c/{localId}"`) makes the driver find it by `localId` rather than by title (with `"sessionRowsBy": "title"` where the rows carry only the title: each such row is pressed until the page's address matches). A `sessionLink` deep link is used only by `show-session` / `open-file`, which bring the desktop to the front anyway; no other command may bring it there. When it cannot, throw an error with the reason (the page shows it); without the capability there is no button.
- Reply Markdown is rendered by the shared `markdown()`, the same for every engine: code blocks with a language name and copy button, highlighted by language (highlight.js), `$…$` / `$$…$$` maths drawn with KaTeX. Your adapter just hands over the original text (with ``` fences); when chats are read from the desktop window, the shared driver turns `AXCodeStyleGroup` back into fenced code blocks.
- **Desktop send (optional; read section 4 of [Choosing channels](channels.md) first)**: when the official channel cannot do what the desktop app can (send as the person, change settings in the desktop app, start chats), use the shared Accessibility driver instead of writing another: `new DesktopAutomation({ engine: '<id>', label: '<desktop app name>' })` (`src/server/core/desktop-automation.ts`); write `src/server/native/<id>-desktop.swift` (steps only; actions are `find / press / fill / open / close / show / current` from `src/server/native/ax-driver.swift`); put the controls' roles and names in `locators` in `src/server/native/profiles/<id>.json` (`role` / `roles` / `name` / `prefix` / `contains` / `after`), plus `bundleId`, `titleSuffix` or `blankTitles`, `sessionLink`, `offscreenMenu` (`press` or `key`), `refreshAnchors`, and, for a shell that is not Electron, `accessibilitySwitches` (the app attributes set to true to turn its web accessibility tree on; default `["AXManualAccessibility"]`; a Chrome-based shell answers only `AXEnhancedUserInterface`, as Codex does since its 2026-11 update, principal class `BrowserCrApplication`). A locator may also say `named: true` (only controls with a name). If your desktop app has a mode switch, also write `spaces`: `{ kind: 'radio' | 'menu', control: <locator name>, currentPrefix?, names: { <space id>: <the desktop's word> }, home: <space id> }` (`radio` is a group of radio buttons whose selected one is the current mode; `menu` is a pop-up button whose name after `currentPrefix` is the current mode, opened to pick the item with that name). Before each command the driver puts the desktop app in the session's mode (`--space <id>`, default `home`; after the switch changes, the page takes a moment to follow, so the driver waits until the page title has that mode's suffix), and afterwards switches back to the person's mode (except `open-file`, which is meant to show that session); if it cannot switch, it does nothing and reports why; if the desktop app shows no such switch, it proceeds as before. The `space` command only reads the current mode and presses nothing. Use `probe` first to see how many matches each locator finds in the real desktop app. The helper's result only says what was done in the interface; whether it was sent is decided by the native record. See Claude's and Codex's.
- `observe(id)`: follow a turn Frontdesk did not start (for example one `create` already started).
- Character, brand colour and skin: see above.

The mode declares `capabilities: CHAT_CAPABILITIES` (exported by the same file: no folders, model, effort, permissions, attachments, steering or stop; the mode's own settings apply).

When read, these are ordinary turns (status evidence `desktop_page`); long chats not read in full carry `metadata.readFromDesktop: { read, total }` and the page explains; when unreadable, return `turns: []` with the reason (sessions in the list carry `metadata.contentUnavailable: '<reason>'` and `sendBlocked` with the same reason, cleared once read). That list can gain the chat late (Codex: about ten seconds after the message went out, measured), so `ChatMode` does not make the person wait for it: while the helper stays on the chat it prints progress lines (`"progress": true`; first `sent`, then `{ messages, running, title }` each time the page changes, delivered through `run(..., { onProgress })`), and as soon as the message is out the chat is handed to the console under an id `ChatMode` gives it. The reply is shown as those lines report it, and once the list has the chat (matched by the title the page gave it) its entry goes by that same id (`realOf(id)` is the desktop's own). Configure `chatSend: { composer, send, stop, newChat, inProject?, noProject?, newShown?, project: ['…{project}…'], projectShown: { locator, may contain {project} } }` (locator names; their meaning is explained in the driver). When the window is not on screen the accessibility tree updates only where acted on, so `refreshAnchors` must include controls this mode also has (Claude added `chatComposer` and "Primary pane").

- **Things the desktop's new-chat page asks for first (optional)**: if your desktop app needs choices before the first message (environment, folder, toggles…) that change with each other, declare `capabilities.newOptions: true` and implement `newOptions()` → `{ controls }` and `pickNewOption(control, option)` → `{ controls }`. `controls` is `[{ kind: 'menu'|'toggle', label, value, options?: [{ label, section, selected }] }]`, read fresh from the desktop app every time, never hard-coded; a toggle's options are `on` / `off`. - **Three things trade memory for time, all in the shared layer, so a new engine just uses them** (`src/server/core/desktop-automation.ts`): (1) **Staying**: while the person chooses one item after another in Frontdesk, the desktop stays on its new-chat page (`--stay`) instead of "open the page → pick → go back" per step; 45 seconds after the choosing goes quiet, or when another command arrives (a message, a card read), the desktop returns to the conversation the person had (`new-leave` / `--previous`); if the page had to be reached in another of the desktop's modes (profile `spaces`), that mode stays borrowed while the person chooses and comes back with the conversation (`previousSpace` in the answer, `--previous-space` to later commands), instead of switching there and back for every step; if somebody is writing on that new-chat page (the check your flow gives `leaveNewPage(inUse:)`: Claude looks for text in the message box, Codex for the Send button, since its empty box reads as its placeholder), if the person is in the desktop app, or if the desktop is in another mode or conversation by then, it is left alone. A flow's own command that reads the new-chat page (Codex's `new-shown`) can honour `--stay` too; call it with `newPage([...])` on the TypeScript side. (2) **Remembering what was read**: the page's controls, and each menu's options for the page as it was then, are kept for a minute (enough for one round of choosing, and a folder the desktop gained since is read next time), so a menu is not opened in the desktop a second time for the same page; after a menu pick, the page's own model and permissions are read only once they have stopped changing (another environment brings its own model); the page's client also keeps, per engine, what was read and chosen, so asking for a new chat again shows it at once and checks it in the background; a first message sent before that check has answered waits for it (a few seconds at most), and a check that failed shows its reason under the cards. (3) **Keeping warm**: optionally implement `keepWarm()` (copy Claude: forward to `DesktopAutomation.keepWarm()`); for a few minutes after a request the page is read every 10 seconds, so the desktop does not put its accessibility tree away and a command never meets an empty page.
- **What is shown was read earlier, so it is checked again before sending**: `create(input)` gets `input.expect` (`[{ control, option }]`, the items Frontdesk shows as chosen, in the page's order), to be checked on the new-chat page before the first message; where the page shows something else it is picked there, and when it cannot be, nothing is created and the reason is given (Claude: `new <folder|-> [<control> <option>…]`, which uses `pickOnPage` and opens no menu for a value already shown).
- **Reading and picking on the new-chat page is done by the shared driver; a new engine writes no Swift for it**: `newPageCommands(open:)` in `src/server/native/ax-driver.swift` provides `new-controls [<control>…]`, `new-pick <control> <option> [<control> <option>…]` and `new-leave` (open the new-chat page once, pick in order, skip menus already showing the target, accept a folder's full path or `~/…`, read only the menus named; by default switch back to the original session at the end, and with `--stay` remain on the page and name the original session in the answer as `previous`). Your flow only writes how to open your new-chat page (`openNewPage`, returning `StepError?`), gives `newPageWatch` a check if needed (Claude uses it to refuse "trust this folder"), and calls `newPageCommands(open: openNewPage)`. How to recognise the page goes in the profile: `newPageHeading` (which heading to read down from), `newPageSkip` (items Frontdesk has its own menus for, such as Model and Permissions), `newPageTogglesAfter` (toggles count from after which locator, such as `composer`), `newPageSkipToggles` (checkboxes whose names start with these do not count). The driver recognises menus as pop-up buttons named `<item>: <current value>`; if your desktop app differs, add a recognition mode to the driver and choose it in the profile, never in your flow. On the TypeScript side, `newControls(read, { fresh })` / `newPick(picks)` come with `DesktopAutomation` (staying, returning and remembered options are inside); an engine's wrapper class has them by extending it. The app name in error text comes from the profile's `name`, and the English translations are already written for any app name.

### The kit (`src/client/kit/`)

Every engine's sidebar, conversation and composer are drawn by the kit; there is nothing to switch on:

### Skin mount points

- **Scope**: the current engine is on `<html data-engine="<id>">`. Every selector in a skin's CSS starts with `html[data-engine="<id>"]`, or it affects other engines.
- **Theme**: `<html data-theme="light|dark">` (absent when following the system; use `prefers-color-scheme`). Match both light and dark. A skin may override CSS variables such as `--bubble`, `--surface`, `--text`, but only within its own scope.
- **Renderers** (registered in `src/client/public/skins/<id>/skin.mjs` via `setup({ registerRenderer, engine, helpers })`; your `turn:<id>` / `session-list:<id>` replace the kit's. This file is a plain ES module the page loads at run time, not compiled by TypeScript or bundled by Vite, declared in the plugin as `skin: { module: '/skins/<id>/skin.mjs' }`):
  - `turn:<id>`: `(turn, { label, provider, markdown, character, escape, icon }) => html`, draws a whole turn (the person's message + the AI's messages and tool activity). It replaces the kit's drawing of the turn for your engine.
  - `session-list:<id>`: `(sessions, { currentId, query, status(item), projects, renderDefault, escape, icon, relativeTime, provider }) => html`, replaces the shared sidebar. Rarely needed; to add something around the shared sidebar, call `renderDefault()` for its HTML and wrap it.
  - `activity:<kind>`, `artifact:<kind>`: a single tool item or artifact card.
  - `plan`: the step card (one, global; to match your desktop app, change `.plan-card` etc. in CSS, or draw it in `turn:<id>`).
- **Model menu**: the `description` from `models()` shows under the option name, `hint` on the right. The menu element has `data-for="model"` so a skin can style it alone.

## 8. Elements and attributes that must stay

Custom renderers and skins must not remove or rename these, or clicking, copying, approvals and scroll restoration break:

## 9. Current limits of the shared code

Found in rehearsals; skins cannot get around them yet. When you hit one, do not quietly change the core; list it in your report under "extension points needed", or use the workaround given:

- Activities sent to the page (`activityOf` in `src/server/core/presentation.ts`) carry neither the native tool name nor a start time. So a skin cannot word things per tool ("opened a page") or show a run time like "2m 8s". Workaround: put the wording you want in `title`; skip the duration.
- `presentHistory` keeps only the fields of the unified shape (including `userImages`); other custom fields on a turn are dropped. For extra data, send it as an activity with `plan` or a dedicated `kind`, and draw it with an `activity:<kind>` renderer (question / summary cards work this way).

## 10. Tests

Cover your parsing and protocol in `test/<id>.test.ts` with test doubles (`node:test`; `npm test` runs it through tsx, and `npm run typecheck` checks the tests too): what counts as a person's input, pairing tools with results, message phases, status evidence, reasons sending is not possible. Never call real services or spend the person's quota in tests.
