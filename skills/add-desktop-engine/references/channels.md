# Choosing channels: how messages get into your desktop app

The hardest part of connecting, and the easiest to get wrong, is deciding which route carries each Frontdesk action (send, steer, stop, change settings, start a chat, answer a card) into your desktop app. This file gives the test first, then how each of the three routes works and which one the existing AIs use, and finally how to write the helper (the Accessibility driver).

## 1. The test: three questions

Ask three questions of any candidate channel:

1. **Is this turn run by the desktop app's own process?** The session's writer lock, context, prompt cache and the desktop app's built-in tools must all be in the desktop app's process. Continuing the same session in another process (a CLI, an app-server you started yourself that resumes it) makes a second writer: the desktop app cannot see that turn, the context forks, and some setups take the writer lock away.
2. **Does the desktop app show the message as the person's own, right away?** Shown as a "system message" or "sent from another app", or visible only after reopening the session, does not count.
3. **Does it avoid anyone else's token?** Never read other programs', other accounts', or the desktop app's inter-process private tokens (philosophy 2 and 2a). Your own official CLI's sign-in credentials may be read on the server at the moment of use.

Three yeses: use it. Any no: try the next route. If none of the three routes works, do not do that action, and say why in the interface (a steer that cannot join falls back to the queue). **Never fall back to "start another process to run this turn".**

Read-only queries (quota, model list, sign-in status) are not subject to question 1: you may start the official CLI for one query that persists nothing and runs no turn (Claude's quota is the control request `get_usage` on `claude --no-session-persistence`). Only actions that write to a session must pass all three.

Decide per action, not one route per engine: Codex sends through the official queue, steers and changes settings through the window-to-window channel, and starts chats through the helper, all three at once.

**Why this order.** All three routes keep the desktop app and Frontdesk in step, since the desktop app does the work either way. Routes A and B are the desktop app's own calls: fast (Codex changes a model in 0.1 s through route B, against 5-7 s through its menus), invisible (no window moves, nothing is pressed), and unaffected by the interface's language or a redesign. Route C works for almost anything a person can do, but it is slow, it briefly moves the desktop window, and it breaks when the interface changes. So route C is the fallback, not the default: **an action that works through route C is still worth checking for route A or B**, and when one is found later, move the action onto it and keep route C as its fallback. Codex's model changes ran through the menus until its window-to-window channel turned out to do the same thing.

## 2. The three routes (best first)

### Route A: the desktop process's own public interface

The desktop app runs a service that outside clients can instruct, while execution stays in the desktop app's process.

- **Codex**: Frontdesk starts its own `codex app-server` and **does only two things on it that take no writer lock**: `thread/read` (read) and `thread/queue/add` (put the message in that session's official queue). Then `open -g codex://threads/wake/<id>` wakes the desktop app, and the desktop's own app-server takes over and runs it. Never `thread/resume` / `turn/start` on Frontdesk's app-server: the writer lock (`~/.codex/thread-writer-locks/<id>.lock`) would land on Frontdesk's process and not be released, and the desktop app would show "This is open in another app". A queued message the desktop has not picked up yet can be withdrawn with `thread/queue/delete` (used for stop). Quota is `account/rateLimits/read`, projects `project/list`, models its model interface. See `src/server/codex-bridge.ts`.
- **Antigravity**: the desktop app's language server listens locally, and `SendUserCascadeMessage` (`messageOrigin: AGENT_MESSAGE_ORIGIN_IDE`) is the very call its own composer makes; the record shows `USER_INPUT`. Steering adds `deliveryStrategy: NEXT_INVOCATION`; stop is `CancelCascadeInvocation`; answering cards is `HandleCascadeUserInteraction`; a new chat in a folder is `StartCascade`. A counter-example from the same app: `agentapi send-message` is recorded as `SYSTEM_MESSAGE` and shown as a system message, failing question 2, so it is never used for the person's words. See `src/server/antigravity-bridge.ts`.

How to find this kind of interface:

- `ps aux | grep -i <app name>` shows the child processes the desktop app started (app-server, language server, daemon) and their arguments; `lsof -nP -p <pid> | grep -E 'LISTEN|unix'` shows the ports and sockets it listens on.
- The official CLI's `--help`, `app-server --help`, protocol export commands (JSON Schema / TypeScript definitions, for example); interface names inside an Electron app's `app.asar` (look read-only with `readAsarFile` from `src/server/services/app-assets.ts`); protobuf descriptors.
- Deep links: `CFBundleURLTypes` in `Info.plist` and the routes in the asar (`codex://threads/…`, `claude://…`). Opening them with `open -g` does not bring the app to the front.
- **Once you have a candidate, verify the three questions with a test session first**: send one message and see whether the desktop app shows it right away, as whom, and who holds the writer lock (`lsof` on the lock file). Write down the evidence; do not judge by an interface's name.

### Route B: the desktop app's window-to-window channel

Some desktop apps have a channel between their windows: one window "owns" a session and the others, as "followers", ask it to act. Frontdesk can briefly connect as a follower and ask the owning window to steer, stop or answer, with the same effect as doing it in the desktop app.

- **Codex**: `~/.codex/ipc/ipc.sock` on macOS, the named pipe `\\.\pipe\codex-ipc` on Windows (`CODEX_IPC_PATH` overrides both). Steer is `thread-follower-steer-turn`, stop is `thread-follower-interrupt-turn` (with `expectedTurnId`), answering a question is `thread-follower-submit-user-input`, approvals are `*-approval-decision`; following a session gives you the requests it is waiting on the person for (`watch`). The next turn's model and effort are `thread-follower-update-thread-settings` (version 2, with a condition on what the owner holds), the very function the desktop's model menu calls; it takes about 0.1 s where the menu takes 5-7 s. Only a session the desktop has loaded since it started has an owner: `thread-owner-discovery` answers within milliseconds when one does, but the router waits 10 s when none does, so stop waiting after 0.5 s. A session with no owner is opened in the sidebar in the background (route C, about 1.5 s), which makes it owned. After a stopped turn the desktop holds its queue (each queued message shows paused until the person sends one), so a message is started with `thread-follower-start-turn` instead: only the message is given, and the owning window fills in the chat's cwd, model, mode and permissions as for a message typed there. See `src/server/codex-desktop.ts` and `pickInDesktop` in `src/server/codex-bridge.ts`.
- Conditions: when no desktop window owns the session, or the turn has ended, fall back to the queue; never resend after a timeout; the native record decides. For versioned protocols, pin the version you verified, and report a reason rather than forcing a send when it does not match.
- A window closed to the tray still owns its sessions: on Windows, with Codex's window hidden, every route B request above and route A's queue + wake were verified (`probes/windows/PLAN.md`).

How to find this kind of channel:

- Sockets and pipes the desktop app holds: `lsof -U -a -p <pid>` (paths such as `~/.codex/ipc/ipc.sock`); on Windows, named pipes (`\\.\pipe\…`).
- Inside the app's `app.asar`, the method names its windows send each other and the versions they expect (Codex keeps a table: `"thread-follower-steer-turn":1`, `"thread-follower-update-thread-settings":2`…), and the handler on the owning side: what each request makes the owner do. A request whose handler calls the same function as one of the desktop's own controls is as good as pressing that control.
- **Probe read-only requests first** (Codex: `thread-follower-read-model-settings`, `thread-owner-discovery`) on a session the desktop has open and on one it has not: how fast an answer comes, and what happens when nobody owns the session (Codex's router waits 10 s, so Frontdesk stops waiting after 0.5 s). Then try one write on a test session, check that the desktop app shows and keeps it, and put it back.
- When the channel needs something only the interface can bring about (Codex: a session is owned only once the desktop has opened it), use route C for that step alone and route B for the action itself, and check by the session's id, not its name, that it worked. Time the whole chain, including the fallback when route B fails.

### Route C: the Accessibility driver (the helper)

For actions neither A nor B can do, use macOS Accessibility (UI Automation on Windows) to operate the desktop app's own interface in the background on the person's behalf: press the session in the sidebar, fill the composer, press Send, open a menu and pick a model. The message's identity is the person's own, execution stays in the desktop app's process, and no token is read.

- **Claude does everything this way**: Claude Code's official channels (CLI / SDK) can only continue a session in another process, which fails question 1. So sending, steering, Send now, stopping, changing model / effort / permissions, new chats, the new-chat page's options, answering question cards and opening a file in the desktop app are all done in the Claude window by `src/server/native/claude-desktop.swift`.
- **Codex does some actions this way**: new chats (pick the project on the New chat page, fill in the message, press Send), opening a chat the desktop has not loaded so that route B can change its settings (and, when route B cannot, the model menu and the "Power" slider, never for a chat whose name another shares), reading the model the New chat page shows, opening files, and chats in its ChatGPT mode.
- **Antigravity does one thing this way**: taking the person to a chat (the chat header's "Open in Antigravity") and to a file in it. Its language server writes but cannot move the window, and its deep link `antigravity://open` takes only a prompt or a project. Its window shows each chat at its own address (`/c/<id>`) and its sidebar rows link there, so the flow is the shared driver's `show-session` / `open-file` with a profile and no steps of its own (`src/server/native/antigravity-desktop.swift`, profile `sessionAddress`). On Windows the same by `src/server/native/antigravity-desktop.cs`, which takes only those two of the shared commands (`sharedTaken`).
- **On Windows** the helper is `src/server/native/uia-driver.cs` with `<engine>-desktop.cs` (UI Automation), the twins of `ax-driver.swift` and `<engine>-desktop.swift`. It sends no keys, but a Chromium page on Windows takes the foreground at every press or fill, which no way found so far avoids (`docs/windows.md`). So the driver parks the window off screen but for a corner while it acts, gives the foreground straight back, waits while the person types in Frontdesk's page, and puts the window back exactly (`probes/windows/PLAN.md`). What that means for your engine:
  - Declare `capabilities.takesFocus: process.platform === 'win32'` when your messages go through the helper (Claude does, and every chat mode: `CHAT_CAPABILITIES`), or `newTakesFocus` when only new chats do (Codex): the page tells the person once, at the first send or the first new chat.
  - With an exclusive full-screen program in front, every acting command does nothing and answers `code: 'fullscreen'`. A send holds the message and tries again (Claude's `sendViaDesktop`: shown as waiting, retried every 3 s, Stop takes it back); a steer throws `fallback: 'queue'`. Anything else that has no run of its own to show it waiting (a new chat, a settings change before a message, a chat mode's message) goes through `throughFullscreen` (`src/server/core/desktop-automation.ts`): tried again every 3 s for up to two minutes, then refused with the reason.
  - A window closed to the tray is not acted on: the command fails and says to open the window from the tray. A desktop app running with higher rights than Frontdesk answers `not_trusted`.
  - Only the driver's window section moves a window or the foreground; a test fails any flow that does it itself or sends input.
- **Both apps' cloud chat modes** (Claude's Claude mode, Codex's ChatGPT mode): their messages are not on disk, so reading, starting and sending all go through the desktop window (`ChatMode` in `src/server/services/desktop-chat.ts`).

The helper's result only says "what was pressed in the interface"; **whether it really went out is decided by the native record** (the message appearing in the session record). How to write it is in section 4.

## 3. Which route each existing AI uses for each action

| Action | Claude | Codex | Antigravity |
| --- | --- | --- | --- |
| Read history | Read-only `~/.claude/projects/**.jsonl` + desktop index | Frontdesk's app-server `thread/read` + read-only JSONL | Read-only record files / language server |
| Send | C: fill the composer, press Send | A: `thread/queue/add` + `codex://threads/wake`; right after a stopped turn, B: `thread-follower-start-turn` | A: `SendUserCascadeMessage` |
| Steer (join the running turn) | C: send as usual; the desktop queues it into the turn itself | B: `thread-follower-steer-turn` | A: same + `NEXT_INVOCATION` |
| Send now (the message the desktop is holding) | C: press the desktop's Send now | — (steering delivers at once) | — |
| Queue (send after this turn) | Frontdesk's RunService queue | Same | Same |
| Stop | C: press Stop | B: `thread-follower-interrupt-turn`; not yet picked up, A: `thread/queue/delete` | A: `CancelCascadeInvocation` |
| Change model / effort / permissions | C: the menus under the composer | B: `thread-follower-update-thread-settings`; a chat not loaded is first opened with C; when B fails, C: the model menu, the Power slider | `requestedModel` with the message |
| New chat | C: the New session page (its options picked first on cards in the page) | C: the New chat page, project picked | A: agentapi / `StartCascade` |
| Answer question / permission cards | C: pick and submit on the desktop's card | B: answer as a follower | A: `HandleCascadeUserInteraction` |
| Open this chat in the desktop app (the chat header's button) | C: shared driver `show-session` | C: same | C: same, found by its id (`sessionAddress`) |
| Open a file in the desktop app | C: shared driver `open-file` | C: same | C: same (its window opens the file in a tab beside the chat) |
| Quota | Official CLI control request `get_usage` (`--no-session-persistence`, runs no turn) | A: `account/rateLimits/read` | Language server `GetUserStatus` |
| Dictation (shared by all) | Official speech recognition with its own credentials | — | Its own |

A new AI finds its place in this table: look for route A first, then route B, and use route C last.

## 4. Writing the helper (route C)

### 4.1 Structure: page objects, three files

| File | What goes in it | Do you write it? |
| --- | --- | --- |
| `src/server/native/ax-driver.swift` | Actions every engine shares: `find / press / fill / open / close / show / current / key`, off-screen refresh, mode switching, reading chats, new-page commands, `check`, `probe`, `inspect`, `open-file`, `space`, `read-chat`, `chat-new`, `chat-send` | No. If an action is missing, add it here so every engine gets it |
| `src/server/native/<id>-desktop.swift` | Your desktop app's **steps**: `send`, `new`, `settings`, `stop`, `answer`… each command prints one JSON object | Yes. Copy the skeleton of `claude-desktop.swift` / `codex-desktop.swift` |
| `src/server/native/uia-driver.cs` | The same shared actions on Windows (`check`, `probe`, `inspect`, `warm`, `restore`, `show-session`, `open-file`…), the park, and the three checks | No. Add a missing action here as in `ax-driver.swift` |
| `src/server/native/<id>-desktop.cs` | The same steps on Windows. `DeclareFlow` names the commands it ports (`flowCommands`); a flow with no steps of its own names the shared ones it takes (`sharedTaken`, as `antigravity-desktop.cs`). Every other command answers `not_ported` | For Windows, yes. Copy `claude-desktop.cs` / `codex-desktop.cs` / `antigravity-desktop.cs` |
| `src/server/native/profiles/<id>.json` | Your desktop app's **data**: how its controls are told apart (`locators`: without their names wherever that is possible, see 4.2), `bundleId`, `name`, the window title suffix, deep-link templates, how menus open | Yes. A renamed control is a change here only. Its `windows` section holds the app's `exe` (how its window is found), `locators` that replace or add to the ones above where the Windows app draws a control differently (an `aria` role where Chromium reports more than the Mac subrole), and `settleMs` / `windowStateFile` where needed |

On the TypeScript side: `new DesktopAutomation({ engine: '<id>', label: '<desktop app name>' })` (`src/server/core/desktop-automation.ts`), or extend it as `src/server/claude-desktop.ts` does, with one method per command. It compiles the driver and your flow into one file (macOS: the Xcode command line tools, cached by source hash in `~/Library/Caches/agent-frontdesk/`; Windows: the `csc.exe` of .NET Framework 4 that Windows ships, C# 5, cached as `%LOCALAPPDATA%\agent-frontdesk\<id>-desktop-<hash>.exe`; rebuilt automatically when the source changes), `check()`s permission and whether the app is running (cached 10 seconds), runs one command at a time (they share one window), and turns `{ model, effort, mode, space }` into `--model` and friends. The JSON the helper prints is a `HelperResult` at this boundary (`{ ok, code?, error?, …other fields unknown }`); your methods narrow the fields they need into concrete types.

### 4.2 Order of work for a flow

1. **Write the profile's `locators`**: one per control, `role` / `roles` plus how it is told apart. A desktop app shown in another language renames every control, so **prefer what the language does not change**, and keep the name as the fallback:
   - Independent of the language: `class` (the element's DOM class, one or several; `"Name-*"` matches by its start, for classes a build gives a new ending), `keys` (the shortcut the page declares for the control, aria-keyshortcuts, such as `"Meta+n"`), `id` (the DOM id, useful only where the page gives a fixed one; a framework's generated `_r_xx_` is not), `subrole`, `url` (the address of a page or a link; `"…*"` matches by its start).
   - Position: `inside` (only within what another locator finds), `after` (only controls after another one), `has` (only what holds a match of another locator inside it, such as "the group that holds the messages"), `index` (the n-th of what is left, from 0; `-1` is the last).
   - Name (changes with the language): `name` (exact) / `prefix` / `contains` / `named: true`.
   - A control may be written as a list: the ways are tried in order and the first that finds anything is the answer. **Put a way that is independent of the language, certain and checked on the real app first, and the name after it**; put a guess by position ("the second menu in the box") after the name, because when the control is absent it finds something else, and because the vendor serves the page and may wrap it in one more group at any time (Claude's message area did within a day).
   - Where one slot shows different buttons in turn and nothing else tells them apart (the corner of Codex's composer: voice / Send / Stop carry the same classes), the locator can only go by the name; do not force a position. For the send button there is also the profile's `sendSlot` (a locator for that slot): where the name finds nothing, the driver's `sendButton` takes "the button there once it was renamed after the composer went from empty to filled".
   - A menu's rows (model, effort, permission mode): first look with `inspect` whether the row has a class of its own or a declared shortcut (each row of Codex's model menu has its own class: `ViewToggle-*` picks the model, the row declaring the arrow keys is the effort slider), and write that as a locator. Where a row carries nothing, the flow finds it by its name first and by its place after, and only when two things hold: the menu shows none of the words the profile knows (the driver's `wordless`), and it has the number of rows expected. Otherwise report why and do not guess. Take a row by its place from the driver's `menuRows(what opened the menu)`, not from `items()`: a desktop app may keep a closed menu's rows on the page (Claude does while its window is off screen), so another menu's rows get mixed in; the profile's `menuPopup` says what a menu's box is, and the page names each box after the button that opened it. The order the places are counted in is the profile's (Claude's `efforts` / `modes`, Codex's `effortOrder`). To accept it: switch the desktop app to another language for real, read once, change once, change back, and switch the language back afterwards (the desktop app's language is the user's to switch, or switched with their consent; a session running inside the Claude desktop app must not change that app's own settings, so ask the user to). Where that cannot be done, the second best is a profile with every word replaced by one the desktop app does not use, but that does not show a half-translated page (Codex in Chinese leaves "Ultra" as it is and translates the other levels).
   - Do not check the result by words alone either: the closed button names the value in the desktop app's language, so it has to agree only where it speaks the profile's words; elsewhere the evidence read while setting it (the slider's status line, the tick) decides.
2. **`inspect` and `probe`**: `AX_PROFILE=src/server/native/profiles/<id>.json <compiled helper> inspect [locator…]` (Windows PowerShell: `$env:AX_PROFILE='src\server\native\profiles\<id>.json'; & "$env:LOCALAPPDATA\agent-frontdesk\<id>-desktop-<hash>.exe" inspect`) lists what the controls those locators find carry besides their names (classes, id, declared shortcut, the boxes around them): write the language-independent ways from it. Then run `probe` to see how many matches each locator finds in the real desktop app: fix any with 0 or several until each finds exactly one. For a locator with several ways, `ways` gives how many each finds and `differ` lists the locators whose ways found different controls. In a language the names match (usually English) `differ` must be empty, in every state of the page (idle, running, text in the composer, the new-chat page, another mode): that is how a way that does not go by the name is accepted. `probe` gives two more: `drift` lists the locators that a way going by a mark of the page (a class, a declared shortcut) no longer finds, though a later way (the name, a place) still does: the desktop app has changed, so `inspect` it again and write the mark as it is now. `several` lists the locators an action would be held back on (see the next point): a control a flow presses or fills must not be in it (locators read with `findAll`, such as a chat's messages, are there by design).
   - **Three checks the driver makes for you** (`ax-driver.swift`, and the same in `uia-driver.cs`; a flow does not write them): (1) **One control, or none, before anything is done.** Looking takes the first match (a look is repeated while the page settles, and reading the whole page costs a few tenths of a second each time). Before a press, a fill or a focus, the driver asks the way that found the control for everything it finds on the page: exactly one, and it goes on; several, with no other way of the locator singling this one out, and nothing is done: the command fails as `ambiguous`, naming the locator and how many answered (the flow's own code is kept as `step`). A way that goes by its place (`index` / `after`) finds one by construction and falls under (2). So do not write a locator as "any `AXTextArea` on the page" and count on the first: make it unique, or say `index`. (2) **A menu button found by its place has to prove itself.** With the control gone, or one more like it added before it, a place finds the neighbour. So the profile's `menuSigns` says, for such a button, what one row of the menu it opens always is (a locator spec that uses marks only: the row's class, the keys it declares, `popup: true` for a row that opens a submenu). A menu that opens without such a row is closed again, nothing in it is picked, and the command fails as `unconfirmed`. A button found by its name or by a mark of its own is not asked. (3) **Every answer says what it stood on**: `via` (the controls found by another way than their first, each `name` / `place` / `mark`), `ambiguous`, `unconfirmed`. About once a minute the server has the warm read check the profile as well (`warm check`: the same reading as `probe`, nothing is pressed); what two checks in a row say has lost its mark is written to the server's log and shown with the engine's status on the page (`DesktopAutomation#staleControls` → `stale` in the engine's status). A desktop update that renames one class leaves everything working in English (the driver falls back to the names) and breaks it in every other language, so the person who only uses English would never notice: this is what notices for them.
3. **Write the flow**: check the result of every step (read the composer back after filling it, confirm a menu really opened, read the button's value again after picking). If any step does not match, `fail(code, reason)` and **send nothing**. Right after pressing Send, ask the driver's `heldBack()`: a press that check (1) held back sent nothing, so put the composer back and report, without waiting for the page to react.
4. **Put things back at the end**: return to the session and mode the person was looking at (the driver's `beforeExit` handles the mode; return to the session with `show` in your flow).
5. **On the TypeScript side, the native record decides**: after the command returns `ok`, watch the session record and count the message as sent only when it appears within a reasonable time (Claude: `sendViaDesktop` watches the JSONL; `steer` uses `waitForRecord` for the `queue-operation`). If it does not appear, report "the desktop app did not receive this message".

### 4.3 Rules

- **Never activate the app or take focus**: presses go through the accessibility tree; keys are posted to the app's process with `postToPid`, not to the screen. Only `open-file` and `show-session` bring the app to the front (the person asked to see it). On Windows the page takes the focus by itself at each action; the driver's park keeps that short, and a flow never moves a window or the foreground itself and never sends a key.
- **Work off screen too**: when the window is full screen in another Space or on another display, Chromium updates its accessibility tree only near the element that received an action. After each wait, have a control from `refreshAnchors` "scroll into view"; while a menu is open the refresh must land on that menu's button (the menu hides the page behind it from the tree). If pressing a menu does not work off screen, set `offscreenMenu: "key"` in the profile (focus the button, then send the down arrow).
- **Dialogs**: confirmations the desktop app puts up that you recognise (Claude's "Switch model?" when changing models, say) are confirmed and their text is carried back to the page; anything else is cancelled and reported as an error. Never enable something the person has not enabled (for example a permission mode marked Enable in the menu).
- **Permission**: without Accessibility permission, return the shared `NOT_TRUSTED` reason. On macOS the Frontdesk server has permission only when started from a terminal (Bash), for example `npm run build && PORT=4131 node dist/server/server.js`. Windows has no such permission; `check` answers `not_trusted` when the desktop app runs with higher rights than Frontdesk.
- **macOS and Windows**: elsewhere `check()` returns "desktop send only supports macOS and Windows"; the interface explains it as usual and nothing is sent. On Windows a command your `<id>-desktop.cs` does not port answers `not_ported`, and with no flow at all `check()` says the Windows port is not there yet.

### 4.4 Reuse instead of rewriting

| You need to | Use |
| --- | --- |
| Handle a mode switch (Mode / Switch mode at the top of the sidebar) | `spaces` in the profile; the driver switches there and back; the `space` command only reads the current mode |
| Pick things on the new-chat page before the first message (environment, folder, toggles) | Write only `openNewPage` in your flow and call `newPageCommands(open: openNewPage)` to get `new-controls` / `new-pick` / `new-leave`; `newPageHeading` and friends in the profile |
| Read the model and permissions the new-chat page shows | Give `newPageShown` a closure; `new-controls` / `new-pick` return it as `shown` |
| Open a file from a reply in the desktop app | `DesktopAutomation#openFile(...)`, the driver's `open-file` |
| Support a cloud chat mode (messages not on disk) | `chatRead`, `chatSend` in the profile; `ChatMode` in TypeScript. Besides `speakers` / `ignore`, which go by words, give `chatRead` the wordless `speakerHeading` (the class of a message's heading), `userMessage` (what follows the heading when the person said it, such as the bubble's class) or `assistantIn` (what the heading sits in when the assistant said it, such as its row's class), `message` (a numbered message's own group; its number is the two numbers in its name) and `skip` (the class of a notice the page adds), and put the container's class before its name. `chatSend.stopSlot`: where Stop takes Send's place and carries nothing else, a locator for that place; where its name is not recognised, the button there is Stop whenever it is not Send (leave it out for a desktop app that shows another button there while idle, such as Codex's voice button) |
| Answer a question card in the desktop's conversation | The driver's `answerCard`; `questionSubmit` / `questionSkip` in the profile |

## 5. Do not

- Start a CLI / SDK process to run this turn, or resume / start a turn on a service of Frontdesk's own (a second writer, a stolen writer lock).
- Read other programs' tokens, cookies or Keychain items; pose as another app over a private socket.
- Activate the app, send global keyboard events, move the mouse.
- Treat a press by the helper as a send: the native record always decides.
- Quietly switch to a route that changes the outcome when a channel is unavailable (for example sending with the old settings when the change could not be made). If it cannot be done, do not send, and say why.
